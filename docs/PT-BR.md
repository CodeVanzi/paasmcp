# 🇧🇷 PaaSMCP — Guia Completo em Português

O **PaaSMCP** é um Micro-PaaS open-source *"Agent-First & Security-First"* (feito sob medida para ser operado tanto por **Agentes de IA via MCP** quanto por **Humanos via Workspace Web e CLI**).

Ele transforma qualquer servidor Linux ou Homelab em uma plataforma de nuvem pessoal automatizada, com **0 MB de consumo ocioso de RAM** quando usado só pelo MCP e pela linha de comando. O painel web e o webhook do GitHub, se ligados, são um serviço sempre ativo (pequeno, mas não zero).

---

## 🎯 Tudo o que o PaaSMCP faz por você

1. **Inicialização Segura (`init` / `paas_bootstrap`):** Prepara `/opt/homelab/paasmcp` com permissão `0700`/`0600`, rede Docker isolada (`homelab-network`), chave mestra AES-256-GCM e par de chaves SSH `Ed25519`.
2. **Cofre Criptografado (`secret` / `paas_secret_*`):** Variáveis de ambiente são criptografadas em repouso com **AES-256-GCM** (IV aleatório por gravação + tag de autenticação). Valores nunca aparecem abertos nas respostas da IA (`sk_l****def`) e chaves inválidas são bloqueadas contra injeção.
3. **Bancos Multi-Tenant + Backups Criptografados (`db` / `db-backup`):**
   - Cria bancos e usuários exclusivos no **PostgreSQL 16** (`db_<app>` / `user_<app>`) ou **Redis 7** e injeta `DATABASE_URL` / `REDIS_URL` automaticamente no container.
   - Gera snapshots (`pg_dump` / Redis RDB / volumes Docker do app) criptografados com a chave mestra do Vault (`.enc.bak`), verifica integridade `SHA-256` e restaura direto em memória sem nunca gravar dump em texto aberto no disco.
   - `paasmcp backup test <id>` prova que o backup volta: carrega num banco temporário e apaga em seguida, sem tocar nos dados em uso.
   - Cópia fora do servidor (R2, B2, S3 ou Garage): coloque `BACKUP_S3_ENDPOINT`, `BACKUP_S3_BUCKET`, `BACKUP_S3_ACCESS_KEY_ID` e `BACKUP_S3_SECRET_ACCESS_KEY` no escopo `system` do Cofre e rode `sudo paasmcp backup install-timer`. Todo dia ele faz backup dos bancos e volumes, envia e apaga do disco local só o que tem mais de 7 dias **e já está fora**.
   - **Guarde a chave mestra fora do servidor** (`paasmcp backup export-key`, num gerenciador de senhas): sem ela os backups de fora não abrem. Num servidor novo, `paasmcp backup fetch <id>` traz um backup de volta.
3b. **Arquivos e imagens (`storage` / `paas_storage_provision`):** cada app ganha um bucket S3 próprio neste servidor, com chave só dele (Garage, que sobe na primeira vez). O PaaSMCP coloca `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION` e os equivalentes `AWS_*` no Cofre do app; basta reimplantar. Por enquanto o endereço só é visível para os apps do servidor (links assinados para o navegador ainda não), e excluir o app de vez não apaga o bucket.
3c. **E-mail (`email` / `paas_email_provision`):** e-mail enviado direto de casa não chega (porta 25 bloqueada, IP residencial em listas de bloqueio), então os apps mandam por um relay (Brevo, SES, Mailgun...) configurado uma vez: `paasmcp email set --host smtp-relay.brevo.com --user <login> --from-domain <seu domínio>` (a senha é perguntada, nunca vai na linha de comando) e `paasmcp email test <seu e-mail>`. Depois, `paasmcp email provision <app>` coloca `SMTP_*`, `EMAIL_FROM`, `EMAIL_URL` (e `BREVO_API_KEY`, se houver chave da API) no Cofre do app, com remetente `<app>@<domínio>`. Atenção: por enquanto todos os apps usam a mesma chave do relay.
3e. **Deploy automático sem webhook (`poll`):** para servidores só no Tailscale, sem endereço público para o GitHub chamar. `paasmcp poll enable <app>`: a cada 2 minutos o último commit do branch é conferido (`git ls-remote`) e o app é reimplantado se mudou. Quem confere é o próprio painel, quando está rodando; sem o painel, um timer do systemd é criado sozinho, sem sudo. O painel também pode se atualizar sozinho a partir da main (`paasmcp dashboard follow` ou o botão "Atualizar sozinho" na linha dele): cada commit novo é compilado e testado numa pasta separada antes de entrar, e se o painel novo não responder em 60 s o anterior volta. No MCP: `autoDeploy: "poll"` no `paas_app_deploy`.
3d. **Atualizações (`update` / `paas_update`):** Postgres, Redis e Garage rodam em versões fixas. `paasmcp update check` mostra versões novas dentro da mesma versão principal; `paasmcp update apply postgres` (pede confirmação) faz backup dos bancos, troca a imagem (as cópias do espelho primeiro), espera até 60 s o serviço responder e, se não responder, volta sozinho para a versão anterior. Trocar de versão principal (Postgres 16 → 17, Garage v1 → v2) é recusado, porque muda o formato dos dados. Com espelho, atualize primeiro o servidor que guarda a cópia.
4. **Buildpacks Zero-Config + Multi-Service Docker Compose:**
   - Detecta automaticamente **Node.js, Next.js, Vite/React/Astro, Python (FastAPI/Flask/Django), Go, C# / ASP.NET Core, HTML Estático** ou `Dockerfile` próprio (o caminho para Rails, Laravel, Java e outras stacks). O painel tem presets de um clique para cada um.
   - Suporta repositórios complexos com `docker-compose.yml`: o PaaSMCP audita e sanitiza o arquivo (removendo `privileged: true`, `network_mode: host` e volumes inseguros do host), injeta o `.env.runtime` do Cofre em todos os serviços e expõe apenas o container web em `127.0.0.1:<porta>`.
5. **Deploy Blue/Green sem Queda:**
   - A nova versão sobe primeiro como container candidato numa porta loopback livre e precisa responder a um healthcheck HTTP (`healthcheckPath`, padrão `/`, status < 500, até 20 s) antes de substituir a que está no ar. Se ela cair ou continuar falhando, a versão atual segue intacta e o deploy devolve os logs do candidato ao agente. Durante a troca o candidato também responde pelo nome do container, então o tráfego do Cloudflare Tunnel continua chegando numa cópia saudável enquanto a produção é recriada (`scripts/bluegreen-lab.sh`). Apps que não falam HTTP usam `skipHealthcheck: true` (`--no-healthcheck` na CLI).
   - **Status do deploy ao vivo:** todo deploy, venha de onde vier (painel, CLI, MCP, webhook do GitHub, timer do `poll`), grava a fase em que está: nova versão encontrada, baixando o código, montando a imagem, testando a nova versão, trocando de versão, no ar ou falhou (com o erro e as últimas linhas do log; a versão anterior segue no ar). A tabela "Seus apps" do painel acompanha ao vivo e mostra o repositório do GitHub, o branch e o commit que está rodando (mensagem, autor e há quanto tempo foi feito), com link para o GitHub. Na CLI: `paasmcp deploys [app]` (`scripts/deploy-status-lab.sh`).
6. **Rollback em 1 Segundo & Diagnóstico `paas_doctor`:**
   - Antes de cada deploy, a imagem funcional anterior é salva como `paasmcp/<app>:previous`. Se o novo deploy apresentar problema, `paasmcp rollback <app>` reverte em 1 segundo sem precisar recompilar.
   - O `paas_doctor` inspeciona containers parados, mortes por falta de memória (`OOMKilled`), contadores de crash e métricas em tempo real (`docker stats`).
7. **Auto-Deploy via GitHub Webhook (`HMAC-SHA256`):**
   - Endpoint integrado `/api/webhooks/github` que valida a assinatura `X-Hub-Signature-256` em tempo constante (`timingSafeEqual`) e reconstrói automaticamente o app quando você dá `git push` na branch configurada.
8. **Dois servidores em espelho (`node`, `mirror` / `paas_mirror`):**
   - Parear: `paasmcp node invite` num servidor e `paasmcp node join` no outro (token assinado, expira em 15 minutos). A sincronização de configuração e Cofre nunca sobrescreve um app que já existe no servidor de destino, e troca a porta se houver conflito.
   - Espelhar: no servidor A, `paasmcp mirror offer B --peer-ip <IP do Tailscale de B>`; ele mostra um comando `paasmcp mirror accept ...` para rodar em B em até 1 hora. B passa a ter uma cópia viva, só de leitura, do Postgres de A, e os backups de B passam a ir para o Garage de A. Repita no sentido contrário para um ser o espelho do outro.
   - Se B ficar fora do ar, A guarda até 10 GB de alterações e B se atualiza sozinho quando volta. `paasmcp mirror status` mostra se está transmitindo, se está em dia e quantos segundos atrás.
   - Troca manual: se A cair, `paasmcp mirror promote A` em B (pede para digitar o nome). B assume os apps de A com a cópia, sobe o número de época, aponta o DNS para si. **Confirme que A caiu mesmo**: se os dois ficarem ligados, cada um aceitaria alterações.
   - Troca automática: só com um **juiz** (árbitro), um terceiro aparelho pequeno (Raspberry, VPS) que dá o voto de desempate. O painel tem o passo a passo em **Segundo servidor → Troca automática**, com botão para testar o juiz e um quadro que mostra se tudo está pronto. Pelo terminal:
     1. Num servidor: `sudo paasmcp arbiter key` (os dois dão a mesma chave).
     2. No aparelho do juiz (Node.js 20+ e Tailscale, sem Docker): clone o repositório, `npm install && npm run build` e `sudo node dist/cli.js arbiter install-service --key <chave>` (fica rodando como serviço, no IP do Tailscale, porta 4097). Para conferir ali mesmo: `curl http://$(tailscale ip -4):4097/health`. Se o aparelho já é juiz de outro par de servidores, não instale de novo: `cd paasmcp && sudo node dist/cli.js arbiter add-key <chave>`. Cada par fica separado, com a própria chave; `arbiter clusters` lista os pares (só um código curto, nunca a chave) e `arbiter remove-key <código>` tira um.
     3. Nos dois servidores: informe o endereço `http://<IP do Tailscale do juiz>:4097` no painel e `paasmcp arbiter check` para testar; `paasmcp mirror auto on A --arbiter http://<juiz>:4097` (pede para digitar o nome) no servidor que pode assumir; e `sudo paasmcp mirror install-watch` nos dois. B só assume se ele **e** o árbitro perderam A por mais de um minuto **e** a cópia parou de receber. Sem árbitro, a troca automática é proibida (numa queda de rede, os dois assumiriam).
   - Cerca: quando A volta e o árbitro diz que B serve os dados dele, A para os próprios apps e recusa deploy até a volta guiada.
   - Volta guiada (A volta a ser o principal):
     1. Em B: `paasmcp mirror offer A --peer-ip <IP de A> --from-copy-of A`.
     2. Em A: `paasmcp mirror accept <token> --rejoin` (o banco antigo de A é movido para o lado, nunca apagado, e A vira cópia de B).
     3. Em B: `paasmcp mirror handback A` (para os apps de A em B e espera A ter tudo).
     4. Em A: `paasmcp mirror promote B`.
     5. Para B voltar a ser espelho: `mirror offer B ...` em A e `mirror accept` em B (a cópia velha é movida para o lado).
   - Mais de dois servidores (estrela): A pode oferecer os dados para quantos servidores quiser (`mirror offer` uma vez para cada um). Todos seguem A, e os apps ativos rodam em todos. Se A cair, o juiz deixa só **uma** cópia assumir; as outras cópias de A ficam "para trás" (o painel mostra), param as cópias dos apps, saem do túnel e nunca assumem sozinhas. Depois da volta guiada, refaça cada uma com `mirror offer` em A e `mirror accept` nela (a cópia velha é movida para o lado). Se A nunca mais voltar, o servidor que assumiu oferece a cópia dele: `paasmcp mirror offer C --peer-ip <IP de C> --from-copy-of A` nele e `mirror accept` em C. C passa a seguir esse servidor e pode assumir os dados de A se ele também cair; até lá, os apps de A rodam só no servidor que assumiu. Sem juiz (troca manual), rode `paasmcp mirror retire A` em cada servidor que **não** assumiu.
   - Por segurança, uma cópia que não recebia nada havia mais de 15 minutos quando A sumiu não assume sozinha (pode estar sem as últimas alterações); dá para promover à mão se for a melhor que sobrou.
   - Testado com containers Postgres reais (`scripts/mirror-lab.sh`: cópia, queda do espelho, troca, volta completa; `scripts/star-lab.sh`: três servidores e juiz real); falta repetir em máquinas separadas.
   - **App nos dois servidores (ativo-ativo, `active` / `paas_active`):** o app roda em A e em B ao mesmo tempo, e os dois recebem visitas. As gravações continuam indo para o Postgres de A; em B o app alcança o Postgres, o Redis e o S3 de A pela Tailscale, com as mesmas variáveis. O painel tem o passo a passo em **Segundo servidor → App nos dois**. Pelo terminal:
     1. Antes: A oferece cópia para B com o IP do Tailscale, e `mirror watch` roda em B (é ele que mantém a versão igual, em até 15 segundos).
     2. Em A: `paasmcp active check <app>` mostra o que falta; `paasmcp active on <app>` (pede confirmação) refaz o deploy da mesma versão e avisa B pelo próprio Postgres, cifrado com a chave do grupo. B monta **o mesmo commit** de A, nunca a ponta do branch.
     3. Entrada com Cloudflare Tunnel: em A, `paasmcp active tunnel on` (pede confirmação) ou o botão no painel. O PaaSMCP cria um túnel só para os apps nos dois servidores, roda esse túnel em A e em B (o token vai cifrado pelo próprio Postgres) e muda o DNS de cada endereço quando a cópia em B responder. Os apps que rodam só em A continuam no túnel atual. Não rode em B o `cloudflared` do túnel principal: a Cloudflare divide as visitas entre os servidores sem olhar o endereço, e os apps que só existem em A dariam erro em B. Com `sudo paasmcp mirror install-watch` nos dois servidores, B sai do túnel sozinho quando a cópia dele fica sem saúde (por exemplo, se a ligação com A cair) e volta quando ela se recupera.
     4. Entrada sem cloud: num servidor com IP público, `sudo paasmcp edge install --email voce@exemplo.com` (pede para digitar `edge`, abre as portas 80 e 443) e `paasmcp edge add <app> loja.exemplo.com`; aponte o DNS (registro A) para o IP público desse servidor. O Caddy pega o HTTPS sozinho, divide as visitas e confere a saúde de cada servidor a cada 5 segundos.
     - Use um caminho de saúde que consulte o banco (`/healthz`) e guarde arquivos enviados no S3, não em volume local. B guarda uma cópia do bucket de cada app ativo, com a mesma chave, atualizada a cada minuto (o que A apaga, B apaga também); arquivos acima de 512 MB não são copiados e aparecem no painel. Migrações de banco devem funcionar com a versão anterior, porque B troca de versão alguns segundos depois de A.
     - Se A cair, a troca automática promove a cópia em B, e o app em B passa a usar o banco e o Redis locais (as sessões guardadas no Redis se perdem) e o S3 local, com as fotos que já estavam copiadas. Na volta guiada, o `mirror handback` devolve para A o que foi enviado em B durante a queda, sem apagar nada. Testado em `scripts/active-lab.sh` e `scripts/files-lab.sh`.
9. **Escala automática (`scale` / `paas_scale`): mede, ensaia e, se você ligar, age:**
   - `sudo paasmcp scale install-timer` liga um timer do systemd que mede a cada 15 s e encerra, sem nada ocupando memória entre uma medição e outra. Cada rodada lê a CPU, a memória e o tráfego de cada app que está rodando (`docker stats`) e cronometra uma resposta do caminho de saúde dele. Ficam os últimos 10 minutos completos e um ponto por minuto por 24 horas, em `paasmcp/scale/`.
   - **Ensaio:** com a escala automática desligada, a regra roda em cima desses números como se o app pudesse ter mais cópias, e só anota o que faria: sobe uma cópia quando a CPU por cópia passa do alvo (70% do limite de CPU do app, ou de um núcleo se ele não tiver limite) em 3 medições seguidas, desce uma depois de 10 minutos abaixo da metade do alvo, e espera 2 minutos entre um passo e outro. Ajuste com `paasmcp scale rule <app> --max 4 --target-cpu 60` ou no painel.
   - **Diário do decisor:** cada decisão do ensaio fica registrada com o motivo, por exemplo “Ensaio: subiria de 1 para 2 cópias. A CPU por cópia ficou em 92% (alvo 70%) por 3 rodadas seguidas (30 s).”. `paasmcp scale diary <app>` mostra; o idioma do terminal, do log e da IA se escolhe com `paasmcp scale language pt|en` (o painel segue o próprio botão de idioma). A IA lê o mesmo diário pelo `paas_scale` para responder “por que o app teria 3 cópias agora?”.
   - **Teste de capacidade:** `sudo paasmcp scale test <app> [--path /]` (pede confirmação) manda requisições GET só para a porta local do app, dobrando quantas vão ao mesmo tempo (até 32, no máximo 64), e diz quantas visitas por segundo uma cópia aguenta e o que travou primeiro: a CPU do app, o banco, erros ou o tempo de resposta. Use um caminho que só lê. O resultado fica no app, no diário e no painel.
   - No painel: **Aplicações → Escala automática**, com gráficos de CPU, tempo de resposta, tráfego e memória, a linha “o ensaio rodaria N cópias agora”, a regra e o diário. Testado com Docker real e gerador de carga em `scripts/scale-lab.sh`.
   - **Visitas por segundo:** quando o app passa pelo balanceador dos PCs ajudantes (com cópias ou com a escala automática), o balanceador conta as visitas de cada app e a regra pode usar um alvo de visitas por cópia (`scale rule <app> --target-rps 20`; o teste de capacidade sugere um valor). Só contam as visitas que chegam pelo Cloudflare Tunnel (ou pelo edge); as que entram pelo Tailscale vão direto ao container.
   - **Cópias em PCs ajudantes (fase 3, `pool` / `paas_pool`, escala manual):** outros PCs seus (um notebook, um desktop) rodam cópias de um app quando você manda, e as visitas se dividem entre este servidor e eles. Este servidor continua sendo o único com Cofre, imagem, banco e entrada; no PC não fica nada rodando entre uma ordem e outra. O painel tem o passo a passo em **Ajudantes → Adicionar um PC**. Pelo terminal:
     1. Aqui: `paasmcp pool invite notebook` (pede confirmação). Na primeira vez, o Postgres, o Redis e o Garage passam a escutar também no IP do Tailscale deste servidor (reiniciam por alguns segundos). O convite vale 15 minutos e uma vez só.
     2. No PC (Linux com Docker, sshd, Tailscale e Node.js instalado para todos os usuários): clone o repositório, `npm install && npm run build` e `sudo node dist/cli.js pool join '<convite>' [--cpus 2 --memory 4g]` (por padrão, metade da CPU e da memória). Ele cria o usuário `paasmcp-worker`, que só aceita a chave deste servidor, só deste IP, e só para rodar o programa do ajudante: sem terminal, sem túnel, sem outros comandos.
     3. Aqui, em até 1 hora: `paasmcp pool add notebook <IP do Tailscale do PC>`. O PC prova que tem o convite antes de entrar, e a chave de acesso dele fica fixada.
     4. `paasmcp scale <app> 3` (pede confirmação na primeira vez e quando passa do máximo da regra) põe 3 cópias no total: 1 aqui e 2 nos PCs com mais CPU livre. `scale off` volta a 1. `pool pause`, `pool resume` e `pool remove` (pede confirmação) controlam cada PC; `pool update-worker` no PC depois de atualizar o PaaSMCP; `pool leave` no PC desfaz tudo.
     - A imagem vai deste servidor para o PC pelo SSH, só quando muda, e é conferida pela impressão digital. As variáveis vão numa pasta em memória (tmpfs) do PC, nunca em `--env`, no disco ou nas configurações do container; somem quando a cópia para ou o PC reinicia (as cópias não voltam sozinhas). Cada deploy, volta de versão ou reinício troca as cópias uma por vez.
     - Só para apps com um container, com caminho de saúde HTTP, sem Zero Trust de preferência, e que não estejam nos dois servidores (ativo-ativo). Use só PCs seus: quem controla o PC consegue ler as variáveis das cópias que ele roda. `paasmcp pool acl` mostra as regras do Tailscale para a tag `tag:paasmcp-helper`.
     - Se um PC some, as visitas que estavam nele se perdem e as novas vão para os outros em cerca de 6 segundos. Se este servidor for isolado (fencing), todas as cópias nos PCs param na hora. Testado com Docker real em `scripts/pool-lab.sh` (dois PCs simulados, PC desligado da rede no meio de 4 visitantes simultâneos).
   - **Escala automática (fase 4, a regra age):** `paasmcp scale auto on <app> --min 1 --max 3` (pede confirmação) ou o botão **Ligar a escala automática** no painel. O app passa pelo balanceador (com 1 cópia, para as visitas serem contadas) e, a cada medição, o PaaSMCP decide sozinho:
     - põe uma cópia num PC ajudante quando a CPU ou as visitas por cópia passam do alvo nas medições seguidas da regra, e tira uma quando as duas ficam abaixo da metade do alvo pelo tempo da regra. Nunca sai do mínimo e do máximo, sobe ou desce um passo por vez e espera entre um passo e outro. Antes de desligar uma cópia, ela sai do balanceador e as visitas em curso terminam;
     - não sobe cópias com o Postgres usando 80% das conexões (cada cópia abre as suas). Se um passo não dá certo (nenhum PC com espaço, cópia que não fica saudável), tenta de novo depois de uma espera que dobra a cada vez (começa na espera entre passos da regra, no mínimo 1 minuto, até 30 minutos), e anota uma vez só no diário;
     - se o servidor reinicia no meio de um passo, a próxima medição pergunta aos PCs o que eles rodam e para as cópias que ninguém conhece.
     - Cada passo vai para o diário com o motivo, por exemplo “Subi de 1 para 2 cópias: as visitas por cópia ficaram em 25/s (alvo 20/s) por 2 rodadas seguidas (10 s). A nova cópia roda em notebook.”. Subir e descer dentro dos limites é livre; ligar a escala automática e aumentar o máximo com ela ligada pedem confirmação; tudo vai para o `audit.log`.
     - `scale auto off <app>` desliga e deixa as cópias como estão. `scale off <app>` (**Parar tudo** no painel) desliga a escala automática e volta o app a uma cópia, só aqui. Precisa da medição ligada (`scale install-timer`). Testado com Docker real em `scripts/autoscale-lab.sh` (dois PCs simulados: carga em degrau e de volta, ondas rápidas, Postgres perto do limite, servidor derrubado no meio de um passo).
   - **Modo cortês (o dono do PC vem primeiro):** a cada minuto, cada PC ajudante diz quanto da CPU dele foi usada fora das cópias desde a última pergunta (nada fica rodando no PC: o PaaSMCP lê os contadores de CPU do PC e das cópias a cada ordem). Se isso passa do limite do PC (50% das CPUs dele, por padrão) duas vezes seguidas, o dono está usando o PC:
     - no modo **automático** (o padrão), as cópias saem do balanceador, terminam as visitas em curso, param e vão para outro PC com espaço (ou esperam o dono liberar);
     - no modo **com aviso**, as cópias ficam e o diário avisa;
     - nos dois, nenhuma cópia nova vai para esse PC. Depois de 5 minutos abaixo de 80% do limite, ele volta a receber cópias.
     - `paasmcp pool courtesy <nome> auto|warn|off [--cpu 50]`, ou o seletor no cartão de cada PC na tela **Ajudantes**. Precisa da medição ligada e do PaaSMCP atualizado no PC (`sudo paasmcp pool update-worker`). Só a CPU conta (memória não). Testado com Docker real em `scripts/courtesy-lab.sh`.
   - **Acordar PCs dormindo (Wake-on-LAN):** um PC ajudante na mesma rede de casa que este servidor pode ficar dormindo enquanto ninguém precisa dele. Quando uma cópia precisa rodar e nenhum ajudante acordado tem espaço (ou um PC com cópia para de responder), este servidor manda um “pacote mágico” para a placa de rede dele:
     - o PC responde em 30 s a 1 min e recebe a cópia, então isso serve para carga que dura, não para picos curtos. A escala automática espera por ele (cerca de 1 min) em vez da espera longa de “sem espaço”, e o diário conta o que aconteceu (“Mandei acordar desk pela rede...”, “desk acordou pela rede: respondeu 42 s depois do primeiro pedido.”);
     - um PC que não responde recebe 3 pacotes, a cada 3 min, e depois o servidor para de tentar até ele responder de novo ou alguém usar **Acordar agora**;
     - uma vez no PC: `sudo paasmcp pool wake-setup` (liga o Wake-on-LAN na placa com cabo, agora e a cada boot; Wi-Fi é recusado porque quase nunca funciona). Para acordar do desligado, e não só da suspensão, ligue também a opção na BIOS/UEFI;
     - neste servidor: `paasmcp pool wake <nome> on` (a placa e a rede vêm do que o PC informou; este servidor precisa estar na mesma rede, e só redes privadas valem), `pool wake <nome> now` para testar, ou o botão no cartão do PC na tela **Ajudantes**. Voltar a dormir fica por conta da configuração de energia do próprio PC. Testado com Docker real em `scripts/wake-lab.sh`.
10. **Confirmações e lixeira (segurança sem cortar funções):** veja a seção abaixo.

## 🛡️ O que a IA faz sozinha, o que pede confirmação e o que é proibido

- **Livre:** status, logs, diagnóstico, medições e diário da escala, deploy, criar banco e backup, reiniciar, voltar versão, expor app pelo Tailscale ou Zero Trust.
- **Pede confirmação de uma pessoa:** excluir app (vai para a **lixeira por 30 dias**, com banco e volumes), restaurar backup (sempre faz um backup do estado atual antes), apagar segredo (o valor antigo fica no arquivo de apagados do Cofre), expor app na internet aberta, expor o painel por Tailscale/Zero Trust, parear servidores, importar pacote de sincronização, convidar ou remover um PC ajudante, pôr um app em PCs ajudantes pela primeira vez ou acima do máximo da regra, ligar a escala automática e aumentar o máximo com ela ligada (subir e descer dentro do máximo é livre).
- **Confirmação forte (digitar o nome):** apagar de vez da lixeira (`purge`) e marcar um app como **confiável** (`--trusted`), o que mantém no `docker-compose.yml` modo privilegiado, rede do servidor, capabilities, dispositivos e pastas do servidor, inclusive `/var/run/docker.sock`.
- **Proibido:** devolver segredo em texto aberto; publicar o painel na internet aberta protegido só por token (use Zero Trust ou Tailscale); portas de app ou banco fora de `127.0.0.1`; `extends` e `additional_contexts` no compose; webhook sem assinatura.

Como a confirmação funciona com IA: a ferramenta MCP não executa e devolve um pedido (`approvalId`, ex. `c-7F3K2A`), que vale 10 minutos e só para aqueles parâmetros. Uma pessoa aprova no painel (cartão "Confirmações pendentes") ou no servidor com `paasmcp approve c-7F3K2A`; depois a IA repete a chamada com `approvalId`. Tudo fica registrado em `/opt/homelab/paasmcp/audit.log`.

Na linha de comando, a pergunta aparece na tela; `--yes` serve para scripts nas confirmações comuns e `--confirm-name <nome>` nas fortes. Para a lixeira expirar sozinha, agende `paasmcp trash purge-expired` uma vez por dia (cron ou timer do systemd).

### IA em outra máquina (MCP pela rede) e dois fatores no painel

```bash
paasmcp token create notebook --level deploy   # o token aparece uma vez; só o hash fica guardado
paasmcp mcp serve --port 4098                  # escuta em 127.0.0.1 (ou --host tailscale)
paasmcp mcp install-service                   # o mesmo, como serviço do systemd no endereço Tailscale (volta depois de reiniciar)
tailscale serve --bg --https=8443 http://127.0.0.1:4098
```

No cliente MCP (Claude Desktop/Code, Cursor, VS Code, Codex, clientes de modelos locais), use `https://<seu-servidor>.ts.net:8443/mcp` com o cabeçalho `Authorization: Bearer pmcp_...`. Níveis do token: `read` (só consultar), `deploy` (padrão: também implantar, criar banco, backup, expor por Tailscale/Zero Trust) e `destroy` (pode *pedir* ações arriscadas, que continuam precisando de uma pessoa). O MCP pela rede só escuta em `127.0.0.1` ou no endereço do Tailscale; ChatGPT e Claude.ai na web precisam de endereço público com login OAuth, que está planejado.

`paasmcp dashboard 2fa enable` liga o código de 6 dígitos no painel (Aegis, Google Authenticator, 1Password…). Com ele ligado, o token sozinho não entra mais, e o painel pode ir para a internet aberta com confirmação forte. Sem 2FA, isso continua proibido.

> Limite honesto: as confirmações protegem contra a IA agindo **pelo MCP**. Um agente que tem terminal no próprio servidor com acesso ao Docker (por exemplo um CLI de IA rodando lá) consegue contornar qualquer regra, porque o grupo `docker` equivale a root. Dê a esses agentes um usuário sem acesso ao Docker.

## 🖥️ Workspace Web para Humanos

Suba o painel web interativo com suporte a temas **Escuro / Claro** e idiomas **PT-BR / EN**. O menu lateral (recolhível; vira gaveta no celular) agrupa as telas em Apps, Servidores, Integrações e Sistema, e as telas maiores se dividem em abas no topo (ex.: **Aplicações → Seus apps / Publicar um app / Deixar acessível / Escala automática / Publicar a cada push**). O endereço de cada aba fica na URL (`#overview/deploy`), então dá para favoritar e usar o botão voltar:

```bash
# Iniciar em 127.0.0.1:4099 e expor em https://paas.seudominio.com protegido por Zero Trust:
paasmcp dashboard start --expose zero-trust --subdomain paas

# Consultar seu token administrativo:
paasmcp dashboard token
```

A interface é dividida em 6 abas rápidas na barra lateral:
- **📦 Aplicações & Deploy:** Tabela com CPU/RAM ao vivo, botões de Rollback em 1s, Logs, Restart, presets de deploy e limites de memória/CPU.
- **🔐 Cofre AES-256-GCM:** Gerenciamento visual de segredos por escopo (`system` ou por aplicação).
- **🗄️ Bancos & Backups:** Provisionamento 1-click de PostgreSQL/Redis e criação/restauração de snapshots `.enc.bak`.
- **🌐 Multi-Server HA & Webhook:** Gerador de Join Token `paasmcp-join://`, exportação de bundle criptografado e URL/Secret do Webhook do GitHub.
- **🩺 Doctor & Diagnóstico:** Inspeção de saúde dos containers e alertas de `OOMKilled`, mais uma conferência do servidor em volta (DNS, Watchtower, redes do Docker e túnel).
- **🤖 Studio IA (MCP) & Guia:** Configuração pronta para copiar em clientes MCP e explicação visual da arquitetura de segurança.

### Instalar num homelab que já tem outros serviços

O PaaSMCP convive com o resto do servidor. Depois de instalar, rode `paasmcp doctor` (ou abra **Diagnóstico** no painel): além dos apps, ele confere o servidor em volta e diz o que ajustar. As armadilhas mais comuns:

- **DNS na mesma máquina.** Se o AdGuard Home ou o Pi-hole roda como contêiner neste servidor e o host usa só ele, o host fica sem DNS quando o contêiner não volta, e junto param o Cloudflare Tunnel, os downloads de imagem e os deploys. Dê ao host uma reserva: `FallbackDNS=1.1.1.1 9.9.9.9` em `/etc/systemd/resolved.conf`, com o `/etc/resolv.conf` apontando para o systemd-resolved.
- **Watchtower.** Ele reinicia contêineres quando a imagem muda no registro. Todo contêiner criado pelo PaaSMCP leva `com.centurylinklabs.watchtower.enable=false`, porque o PaaSMCP fixa e atualiza as próprias imagens. Os contêineres criados antes ganham o rótulo na próxima recriação; o Watchtower com `WATCHTOWER_LABEL_ENABLE=true` resolve na hora. Pause o Watchtower enquanto testa o ativo-ativo ou a escala.
- **Redes do Docker.** O Docker usa primeiro 172.17 a 172.31 e depois 192.168.x.0/20, que pode cobrir uma rede de casa como 192.168.31.0/24. Ponha `"default-address-pools": [{"base": "10.200.0.0/16", "size": 24}]` em `/etc/docker/daemon.json` antes de chegar lá.
- **Portas.** Os apps usam portas de loopback 4000-4998, pulando 4097 (juiz), 4099 (painel) e qualquer porta já em uso. A entrada própria (`paasmcp edge on`) precisa das portas 80 e 443 livres; com Nginx Proxy Manager ou outro proxy nelas, fique no Cloudflare Tunnel ou ponha a entrada em outra máquina.
- **Seu próprio contêiner do Cloudflare Tunnel.** O PaaSMCP manda os endereços públicos para os apps pelo nome do contêiner na rede Docker `homelab-network`, então o contêiner `cloudflared` precisa estar nela.
- **Servidor no cabo.** O ativo-ativo e o juiz julgam um servidor por ele responder; Wi-Fi instável gera falsos alarmes.

### Primeira configuração e credenciais

As integrações externas são opcionais. Bootstrap, deploy de pastas locais, repositórios públicos, bancos locais e uso do painel não precisam de token Cloudflare ou GitHub. Guarde credenciais em **Cofre → escopo `system`**; segredos usados pelo código de uma aplicação ficam no escopo do slug dela. O painel mostra valores mascarados depois de salvar.

| Item | Quando é necessário | Como obter/configurar |
| --- | --- | --- |
| `DASHBOARD_TOKEN` | Entrar no painel | Gerado automaticamente. Consulte no host com `paasmcp dashboard token`; não é necessário criar token externo. |
| Chave SSH Ed25519 | Clonar repositórios privados por SSH ou usar chave de deploy | A chave é criada no bootstrap. Em **Aplicações → Publicar a cada push**, copie a chave pública e adicione em GitHub → repositório → Settings → Deploy keys. Mantenha acesso somente leitura. |
| `GITHUB_TOKEN` | Opcional: registrar a Deploy Key via API ou clonar repositório privado por HTTPS | Crie um fine-grained personal access token, restrito ao repositório necessário, com `Administration: read and write` para a API de Deploy Keys. Essa permissão é exigida pelo endpoint do GitHub mesmo quando a chave registrada é somente leitura. Se não quiser concedê-la, adicione a chave SSH manualmente e deixe o token vazio. [Criar token](https://github.com/settings/personal-access-tokens/new) · [Permissões do endpoint](https://docs.github.com/en/rest/deploy-keys/deploy-keys#create-a-deploy-key). |
| `CF_API_TOKEN` | Opcional: publicar via Cloudflare Tunnel/DNS; também cria política Access no modo Zero Trust | Crie token restrito à conta e zona usadas. Necessário: Account → Cloudflare Tunnel: Edit e Zone → DNS: Edit. Para Zero Trust, inclua Account → Access: Apps and Policies: Edit. [Criar token](https://dash.cloudflare.com/profile/api-tokens) · [Guia oficial de tokens](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/). Salve-o no Cofre `system`. |
| Account ID, Tunnel ID e domínio base | Exposição via Cloudflare | Obtenha Account ID na área Overview da conta, Tunnel ID na lista de Tunnels e use um domínio cuja zona DNS esteja na Cloudflare. Configure por `paasmcp config --account-id ... --tunnel-id ... --domain ... --zero-trust-emails ...` ou MCP `paas_configure`. Para Zero Trust, informe os emails autorizados. |
| `WEBHOOK_SECRET` | Opcional: rebuild automático ao receber Push do GitHub | Gerado automaticamente pelo PaaSMCP. Em **Aplicações → Publicar a cada push**, copie a URL e revele/copiei o secret; no GitHub → Settings → Webhooks, crie webhook com Content type `application/json`, secret correspondente e evento `Push`. O endpoint precisa estar acessível pelo GitHub. |
| `CF_API_TOKEN` não necessário com Tailscale | Publicação privada via Tailnet | Instale e autentique Tailscale no host; use o modo Tailscale. Não requer DNS Cloudflare nem credencial adicional no PaaSMCP. |

**Fluxo recomendado:** (1) inicialize com `paasmcp init`; (2) recupere o token do painel; (3) para código privado, escolha Deploy Key SSH manual ou token GitHub restrito; (4) configure Cloudflare somente se for publicar por Tunnel; (5) faça deploy e adicione segredos próprios da aplicação no escopo do app; (6) confira Logs/Doctor e publique serviços com autenticação própria como públicos, reservando Zero Trust/Tailscale para interfaces administrativas.

Para o primeiro teste, use uma pasta local ou repositório público e um preset SPA; não configure tokens externos até que uma funcionalidade precise deles. PostgreSQL/Redis podem ser provisionados durante o deploy e as URLs são injetadas no escopo da aplicação.
